# ZLOZ product North Star

**Status** · Approved product direction, 24 November 2026. This is the design reference for the Teams workspace. The milestones below are delivery proposals. The baseline describes merged source at `39e8dd24`.

A facilitator opens ZLOZ, finds the team’s returns board and places an event. A colleague adds a hotspot. Both can tell when the edit has reached the shared board. Later, one person rewinds to the moment the hotspot was resolved while the other continues working. **Design for that session from beginning to end.**

Use this document when deciding where a feature belongs. A change should make it easier to **find the board, do the work, or explain what changed**. Keep the team’s boards at the centre of team home and the diagram at the centre of the editor. Put new commands into an existing menu before spending permanent canvas space. Review changes to these principles here. Record delivery and qualification evidence against the relevant milestone.

## Team home and settings

**Boards is the team landing page.** Keep the team switcher, board search, **New board** and **Import** at the top. Start with a compact list sorted by last update. Give names room, show last updated time, and preserve the search and scroll position on return. Use distinct empty states for a new team, a search with zero matches and a failed load. A viewer gets a clear route to open a board and an explanation of how to request editing access.

**Create and name in one step.** Open a small naming dialog with focus in the field. Enter creates one board and opens it. A failed submission keeps the name and explains how to retry. On a fresh board, offer a mode-appropriate first action and **Import** in place. Import opens the existing preview, reports generated elements and losses, and lets the editor cancel or apply to that same eligible empty board. Recheck eligibility if a teammate edits during the preview.

| Location       | What belongs there                                                              | Who controls it                                                                       |
| -------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| My preferences | System/light/dark, reduced motion, optional persistent tool labels              | The individual. A personal change should never surprise a teammate.                   |
| Team settings  | Members, invitations, roles and access to the team’s shared icon library        | Owners administer membership. Asset actions respect the existing library permissions. |
| Board settings | Board name and shared appearance, including a chosen background where supported | Authorised board editors. Make the shared effect explicit before applying it.         |

## The working board

Use the existing mark with **ZLOZ** in the app header, sign-in, invitation and browser title. Keep technical package names in developer material. Give light and dark equal care, including selection, ghosts, charts, conflict states and focus rings. Use readable type for names and notes. Reserve monospace for values people compare, such as version, zoom and chart ticks.

| Position | Interaction                                                                                                                                                                                                                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Top      | Team and board breadcrumb, visible mode, collaborators and save status. Group commands under familiar desktop menus. Use **File** for import/export, **Edit** for Undo and find, **View** for focus and history, **Arrange** for ELK, align and distribute, and **Help** for controls that work in the active mode. Display shortcuts beside commands. |
| Left     | A compact tool rail for select, pan, place and connect. C4, DDD and Event Storming have distinct palettes. Event Storming exposes events, hotspots, commands, policies, actors and external systems. Keep Questmancer accessible through its own workspace entry.                                                                                      |
| Right    | A collapsible inspector for selection, OPY relationship decisions and analysis. A chart selection can focus the corresponding board item. Closing a panel returns focus to the invoking control.                                                                                                                                                       |
| Bottom   | Stable zoom, fit and **History** controls. In focus mode both side rails collapse. At narrow widths, use one dismissible drawer at a time. Long lists scroll inside their panel. Primary controls remain reachable without scrolling the board page.                                                                                                   |

Use Phosphor icons for frequent tools and short visible labels for **New board**, **Import**, **History**, **Back to live** and conflict recovery. Give icon controls accessible names, focus and hover hints, selected states and generous hit areas. Prefer the catalogued `@foldkit/ui` primitives for menus, dialogs, tooltips and comboboxes. Adapt the existing SDK scrubber to the ZLOZ visual design. Wire each surface to the same command and enablement rules so keyboard, menus and pointer agree. [FoldKit UI precedent](../../tech-radar/src/radar/three/view.ts) · [Team style tokens](../src/styles/workspace.css.ts)

Evaluate the controls with three questions from Nielsen Norman’s heuristics. Can someone recognise the tool before using it? Can they tell what happened afterwards? Can they recover from a mistake? In a keyboard walkthrough, Tab should reach the toolbar as a group, arrows should move between its tools, and Escape should close an open menu and restore focus. Test whether users can identify icons in the context of a real task. [NN/g on heuristics in complex applications](https://www.nngroup.com/articles/usability-heuristics-complex-applications/) · [WAI toolbar pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/)

## Rewind and workshop journeys

**Rewind should feel like operating a small tape deck.** One activation of **History** opens a shallow strip against the bottom edge. Use a ruled scale, a precise playhead, previous/next, play/pause and a version counter. Keep the canvas in view. Dragging scrubs continuously, arrow keys step a version and a screen reader announces the selected version. Expose **Compare** and **Back to live** in the strip.

```text
Previous   Play   Next     ├──────●────────┤   v128   Compare   Back to live
Read-only · Versions 101–128 this session                      Live v131
```

Compare pins a baseline and adds ghost outlines with a readable list of changes. A resolved hotspot should read **Open → Resolved**. Reviewing is local and read-only. A colleague’s incoming update advances the live indicator while the review playhead stays put. If a gap or eviction makes the chosen version unavailable, explain what happened and offer the available range and **Back to live**. A single observed version gets an honest empty state for comparison.

**Use FoldKit Viz to answer questions that lead back onto the canvas.** C4 Board’s Evolution panel gives the facilitator a compact view of how a diagram developed. Carry that interaction into Teams with our Viz primitives and shared data. [C4 Board reference](https://github.com/opsydyn/c4-board/blob/2b20af660f9300624cc151b7599022126d8c3949/src/ui/components/DiagramEvolutionChart.tsx) · [Teams Evolution chart](../src/editor/evolution-view.ts)

| Workshop question                           | What the editor can do                                                                                                      | What the data must support                                                                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| When did hotspots open or resolve?          | Select a point on the events and open-hotspots chart to inspect that confirmed version. Inspect the changes or return live. | Count from confirmed snapshots, including Delete and Undo. Show the session window, interruptions and a keyboard-readable table.                 |
| How does a case travel through our process? | Select a starting event, follow its authored links, choose a branch and focus each note and edge on the board.              | Use typed, authored causal relationships. Show gaps, forks and revisited nodes explicitly. Moving notes on the canvas must preserve the journey. |
| Which relationships need discussion?        | Pick an abstraction scope and change horizon in Balanced Coupling, inspect a mark and select its relationship.              | Preserve qualitative outcomes and unknown inputs. Show why an orbit is empty and keep the evidence table available in either theme.              |

## Feedback and observability

Connect delight to an event people care about. Draw a new edge once, let a placed note settle briefly, and give a newly raised hotspot a short coral flare. Reconnect renders the current board quietly. Reduced motion uses a stable outline, symbol and text. Test feedback while dragging so animation never takes pointer capture, shifts a hit target or delays local feedback.

| Question                     | Signal and expected behaviour                                                                                                                                                                                                                                                           |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Did my gesture register?     | Measure release to first local paint on the originating device. A pending save keeps its displayed geometry. Record a local baseline on the pilot Mac before setting a budget.                                                                                                          |
| Did the team accept my edit? | Distinguish pending, confirmed, rejected/conflicted and reconnecting. A conflict offers a way to inspect the confirmed state and reapply deliberately. Target **zero rejected edits shown as Saved**.                                                                                   |
| Did my colleague see it?     | Correlate submission, server decision and peer paint with an opaque operation ID. Use the qualification harness’s single-clock measurement or a peer acknowledgement for end-to-end timing. Report missing renders and failures in the denominator.                                     |
| Can we trust reconnect?      | Compare the two editors’ confirmed versions and positions after reconnect. Retain the existing five-editor qualification gates of p95 under 1,000 ms for submission to all-peer DOM acknowledgement and catch-up under 10,000 ms. [Frozen workload and measurement](staging-runbook.md) |

Keep operator traces separate from user-visible status. Capture durations, outcomes, mode and connection state. Exclude board content, user emails, asset bytes and prompts. Collect a short trace on a conflict or reproducible stall. The previous CPU investigation stays parked unless new product evidence warrants reopening it.

## Delivery and review gates

The order is deliberate. Each milestone leaves a complete user journey available for review. Use the exit criteria below to review each milestone.

| Milestone                             | Deliverable                                                                                                                                                        | Ready for the next review when…                                                                                                                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1 · Find a board and start a workshop | Prototype team home, settings navigation, the ZLOZ wordmark, and **New board → name → place first event** in both themes. Then wire the directory and create flow. | An owner and editor can find an older board and create a named board unaided. A viewer can find and open the same board. A fixture with at least 101 boards exposes the oldest result and excludes another team’s boards. Retry creates only one board.            |
| 2 · Work on one canvas                | Ship the menu bar, compact tools, settings surfaces and focus behaviour. Move existing commands into the shell. Instrument the save path before adding motion.     | At 1280 × 720 and at a narrow touch width, users reach primary controls with both rails closed and through a drawer. Verify keyboard, VoiceOver, both themes and reduced motion. Two editors can edit during Saving, see conflicts and converge after reconnect.   |
| 3 · Explain what changed              | Deliver the rewind transport, meaningful ghost labels and Event Storming Evolution. Make the scope and horizon for Balanced Coupling discoverable.                 | One editor resolves, deletes and undoes a hotspot while a peer scrubs and compares. Chart counts agree with confirmed snapshots. Review writes zero edits. The peer can return to the latest board after a gap. Capture a keyboard replay and light/dark examples. |
| 4 · Follow an authored journey        | Prove typed causal relationships through Teams authoring, sync and reload. Add the interactive journey view and its text equivalent.                               | Follow a real branching process with a gap and a loop. Each step focuses the correct note or edge. Moving a note preserves the path. Two editors and a reconnected viewer see the same authored structure.                                                         |

**Milestone 1 review build.** The [local browser exercise](../test/runtime.test.ts) covers a team with 102 boards, the owner/editor/viewer journeys, retrying creation and returning to filtered results. The fixture verifies permissions and persistence. Use the session below to judge whether people can discover the controls unaided.

**Milestone 2 review build.** File, Edit, View, Arrange, Help and a direct History control are available with both rails collapsed. Arrange opens a local preview before Apply. History resolves the latest confirmed version when opened. The [render-work regression](../test/view-work.test.ts) checks that a peer rename stays within the existing control rebuild budget. Keyboard, VoiceOver, touch placement and the two-editor replay belong to the combined end-to-end review.

**Settings and tools review build.** My preferences stores the theme and compact or labelled edit tools in this browser. Board settings shows the current role and gives owners access to checkpoint recovery. Team settings manages membership. Compare the icon-only and labelled Undo and Delete controls in the keyboard and touch review.

**Rewind review build.** The ruled scrubber sits below the historical canvas. Its range is pinned to the confirmed session window at entry. A peer edit advances the live counter while the reviewed version stays selected. **Back to live** returns directly to the current board. Workshop ghosts and the differences list show the same baseline-to-reviewed change, including hotspot resolution, reopening and movement. Verify trackpad scrubbing, focus and touch placement during the combined design replay.

**Workshop Evolution review build.** In Event Storming view, Diagram Evolution shows domain events and open hotspots at each retained confirmed version. Select a point, or use **Inspect version → Open on canvas**, to rewind. When the preceding version is in the window, the comparison opens with it as the baseline.

**Balanced Coupling review build.** The inspector shows the authored abstraction scope, time horizon and assessment model ahead of the orbit. Its comparison count covers current outcomes across the selected group. The orbit covers the current page. In the all-scopes table, each recorded assessment shows its context before the evidence disclosure.

**Workshop causal link review build.** In Event Storming, choose **Connection meaning → Produces** and connect a command output to a domain event input. Choose **Activates** to connect that event’s output to a policy input. A [local regression](../test/workshop-link.test.ts) authors the two links across two editor models, moves the middle event and reloads the serialized board. The connection list retains both directed relationships. The two-browser replay belongs to the full design pass.

**Journey review build.** In Event Storming, open **Inspector view → Workshop journey**, choose a starting note and follow its confirmed Produces, Activates or Triggers links. The FoldKit Viz overview shows directed branches and loops. A ring marks the current note and the caption gives the step number. Each step brings its destination into view. Select any note or relationship in the trail to reveal it again. A policy can trigger a command. Returning to a note marks the visit with its first step number. The trail scrolls independently so the overview and **Back one step** stay in view while reviewing a branch. A terminal note names the end of the path. Journey navigation is local and available to viewers.

**First review session.** Give the facilitator a team with an older “Returns” board and ask them to find it, then start a new returns workshop. Ask a second editor to place a hotspot and a viewer to describe what changed. Observe first click, time to first confirmed event, wrong turns, requests for help and whether participants distinguish live from review. Repeat one task keyboard-only. Link anonymised observations, screenshots and traces to the milestone, and record where a participant needed coaching.

**Decisions for the first review.** Is the compact list enough to recognise a board by name, or do participants need a thumbnail? Can they find History without knowing the inspector? Can they identify the scope of a setting before changing it? Use the failures to choose the next revision. Rich previews, durable cross-session history and inferred journeys each need a separate product decision.
