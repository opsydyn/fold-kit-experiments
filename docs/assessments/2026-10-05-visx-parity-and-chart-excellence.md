# Foldkit Viz: visx parity and chart excellence

Date: 2026-10-05. Local source baseline: `e28304a`, managed promo worktree, branch `codex/foldkit-0-166-0`.

This is a source-grounded assessment and proposed roadmap, not an implementation plan or release claim. The latest bar/cloud APIs are committed locally and documented as unreleased. Public npm and Pages availability must be verified separately.

## Intended outcome and recommendation

A developer should be able to compose a trustworthy instrument for investigating a system, or an expressive visualisation that invites useful exploration, using the same pure geometry and explicit Foldkit state. First useful success: load caller-owned records, compare two views, inspect an exact observation and explain what is selected, missing or uncertain.

**Pursue a shared foundation with two visual directions.** Precision and delight should share data identities, scales, selection, measurement, accessibility and provenance. Presentation can vary substantially. Precision means that a visual claim is traceable and testable; delight means that a surprising interaction makes a pattern easier to discover or understand.

Observed: the repository has broad geometry, application-level chart examples, reusable Cartesian adapters, six live promo explorers and an eighteen-chart promo gallery. Inferred: interaction composition and qualification offer more immediate value than adding another broad batch of chart types. Unknown: customer demand, operating contexts, adoption and real-task performance. A competitor checklist does not establish those.

Assumed first contexts: engineering telemetry and analytical data exploration. These are design fixtures, not claims that a critical-system deployment has been validated. No commercial, regulatory or operational suitability claim follows from this roadmap.

Three routes considered:

| Route                                                               | Benefit                                                               | Tradeoff                                                             | Recommendation                                                       |
| ------------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Copy every visx example first                                       | Clear breadth and familiar demonstrations                             | Risks expanding the gallery faster than the shared APIs and evidence | Use as an inventory, not the delivery order                          |
| Build a shared interaction foundation and two reference experiences | Reuse is visible; precision and expressiveness can be tested together | Fewer new thumbnails initially                                       | Recommended                                                          |
| Keep existing primitives and document app recipes only              | Lowest package scope and migration cost                               | Consumers continue owning repeated plumbing                          | Retain for specialised recipes until reusable demand is demonstrated |

Status vocabulary:

- **Public**: a corresponding exported primitive/adapter exists. This does not establish complete visx semantics or native acceptance.
- **Partial**: public support covers only part of the behaviour.
- **App**: an implementation exists in the demo/application; a reusable package contract is absent or narrower.
- **Build**: no dedicated corresponding primitive/recipe was found in the audited source.
- Promo **Live** means a dedicated explorer; **Tile** means a gallery rendering; **Indirect** means another explorer demonstrates the capability; **Absent** means no dedicated promo presentation.

Priorities are proposed: **P1** composition and dependable inspection; **P2** analytical breadth and expressive presentation; **P3** specialised parity after a concrete use case. Do not infer a percentage parity score from unlike units.

## Two reference experiences

### Signal desk: an incident investigation instrument

Use synthetic, explicitly labelled system telemetry with timestamp, signal, value, unit, quality, source revision and optional caller-supplied interval. Compose an overview, a precise detail chart, an event lane and a record table. Brush a period, zoom into a spike, compare related signals, freeze a cursor and inspect provenance. Include empty/loading/stale/error fixtures and a late-arriving sample.

First slice: interval brush + zoom + linked cursor + table, using F1–F3. Subsequent precision work adds quality and uncertainty only after that composition is stable. Alarm thresholds are application inputs, never conclusions generated by Viz.

### Foldout atlas: an expressive comparison explorer

Use illustrative community activity records with dates, groups and distributions. Unfold a compact overview into small multiples; change the view to a raincloud; follow one group through a flow view. Keep one selected record/group and the same units visible throughout. Use saturated colour, crisp rules, measured type and restrained patterned ink. Offer daylight/dark/print recipes.

First slice: J1 using existing bars and parent-owned selection. J2 adds a second analytical perspective. Novel time layouts and flow motion are optional later recipes, contingent on comprehension evidence.

Proposed learning appetite: four focused engineering days for M1, including qualification and a comprehension check; this is a suggested cap, not an estimate or accepted budget. Allocate two days to coordinate/interaction contracts, one to the reference composition, and one to fixtures/native checks and task review. Proposed learning tasks with three representative developers/analysts, recruited only through separately authorised activity: identify a spike and its raw value, isolate its interval, distinguish missing from zero, compare a related signal, and explain the chosen view. Primary measure: unassisted correct task completion; baseline unknown. Proposed threshold: all three distinguish missing/zero and retrieve the exact record, and at least two complete the linked selection without guidance. Small qualitative results indicate friction, not population success rates or market demand. Incorrect interpretation caused by an expressive form blocks that form; repeated interaction confusion reshapes M1. Inconclusive results extend neither scope nor budget automatically. If representative participants are unavailable within the learning window, finish the technical evidence and record comprehension as untested; do not substitute engineering acceptance for that evidence.

## Definition of chart excellence

Every accepted chart/recipe should carry a small evidence record:

1. **Analytical claim:** what question it answers, quantities/units, scale/domain, aggregation and meaningful omissions.
2. **Geometry:** finite output, declared invalid-input policy, supported boundary conditions and per-algorithm reference/property tests. Extreme magnitude, cancellation, degenerate domains, repeated keys and sparse data are deliberate fixtures.
3. **State:** controlled keys and selection; stale async completions cannot replace current data; identity persists across sorting/filtering/resize; side effects occur only at runtime boundaries.
4. **Perception:** measured label layout, explicit baseline, distinguishable series without colour alone, legible light/dark/print output, and no texture that masks a critical boundary.
5. **Interaction:** local coordinates, keyboard and touch, focus retention, cancellation, stable inspection and observable recovery.
6. **Performance:** recorded dataset, render density, device/browser and p50/p95 update/memory measurements. No performance claim from a thumbnail or unit test.
7. **Evidence:** focused tests, external consumer, native browser checks, static export comparisons and any publication proof recorded separately. Native accessibility task acceptance is distinct from generated ARIA markup.

For proposed accessibility targets, use [WCAG 2.2 contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 4.5:1 for ordinary text, 3:1 for qualifying large text; use [non-text contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) for meaningful graphical objects. Meeting these targets alone does not establish overall accessibility conformance.

## Deliberate deferrals

- No rewrite of Foldkit into React-like context/hooks or a second state runtime.
- No full React API compatibility or exact package-count target.
- No automatic statistical conclusions, forecasting, alarm policy or domain certification.
- No 3D, ambient sound, generative chart choice or GPU rewrite without a task that needs it.
- No pixel-mask cloud or globe projection overhaul before a use case demonstrates the current limit.
- No migration of every existing web chart in one release; qualify representative contracts first.

Next proposed action: specify M1 as a bounded interaction/composition project, with exact public contracts and regression fixtures. The roadmap does not authorise that implementation.
