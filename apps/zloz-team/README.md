# ZLOZ Teams

Astro app for the invited-team MVP, alongside the existing public local workbench.
M1 supplies invited-team onboarding; M2 supplies shared graph operations and the
optional Alchemy adapter. M3 connects the shared browser editor with create/import,
live updates, confirmed-state export, conditional Undo, retry and transient presence.

The [ZLOZ product North Star](docs/product-north-star.md) guides Teams design decisions and sets the review gates for the UX roadmap.

From the repository root:

```sh
cp apps/zloz-team/.env.example apps/zloz-team/.env
bun run dev:zloz-team
```

Open `http://localhost:4331`. The app uses a fixed port because auth origins must
match; set both `ZLOZ_PORT` and `ZLOZ_ORIGIN` when choosing another one. Google
sign-in is disabled until the local environment has valid provider credentials.
The app never offers public team creation. Alchemy generates and persists the
signing secret in ignored local state; retain it to keep sessions across restarts.

The default stack permits `alchemy dev` only and uses local state and local
Workers/D1. M4 adds a separate guarded staging entry and hostname; see the
[staging and recovery runbook](docs/staging-runbook.md). Existing ZLOZ hosting is
untouched. Alchemy beta.85 needs the explicitly pinned workerd override in
`tools/dev.ts` and `tools/build.ts` for the 2026-11-11 compatibility date.

```sh
bun run --filter @opsydyn/zloz-team build
bun run --filter @opsydyn/zloz-team typecheck
bun run --filter @opsydyn/zloz-team test
bun run --filter @opsydyn/zloz-server test
```

Tests start an isolated local stack on temporary ports, with a separate stage
and a bearer-protected test fixture Worker. It seeds real signed sessions and
organization rows; it does not simulate a successful Google OAuth exchange.
That fixture is imported only by the guarded test stack and is absent from the
application topology. Native runtime tests need permission to open local ports.
Their execution logs are written to `zloz-team-runtime-*.log` in the system temporary directory.

The local launcher defaults to Alchemy's JSON log format, retaining log levels
and records while avoiding pretty timestamp formatting on the development host.
Set `ALCHEMY_LOG_FORMAT=pretty` explicitly for interactive debugging. Run full
load qualification separately with `bun run --filter @opsydyn/zloz-team qualify:load`;
`ZLOZ_LOAD_REPORT=/absolute/path.json` retains its entire planned population.
Optional `ZLOZ_C11_CPU_PROFILE=1` records browser profiles alongside that report;
`ZLOZ_C11_CLI_PROFILE=/absolute/existing/directory` records launcher/CLI profiles.
Profiles are diagnostic runs; repeat qualification without profiling. The guarded
qualification fixture adds backend `Server-Timing` phases; ordinary app/staging
requests do not enable this probe.
Local development also opts out of Alchemy CLI usage exports by default through
`ALCHEMY_TELEMETRY_DISABLED=1`. This removes its external one-second export loop
from the local service-binding host; application telemetry, local CLI logs and
browser warnings stay enabled. An explicit empty value opts back in, subject to
Alchemy's other user opt-out settings. Staging/deployment commands are unchanged.
The editor keeps FoldKit's default slow-phase thresholds and logs every warning
as phase, elapsed time and budget. It omits model/message payloads so Vite's
console forwarding cannot serialize the whole document for each slow phase.

Auth schemas and membership constraints belong to
[`apps/zloz-server`](../zloz-server). A request checks current membership before
Domain receipt lookup and again during each decision/live delivery. A 25-second
socket lease forces idle clients to reconnect through current auth. The browser reconnects through that boundary and reconciles canonical document
versions and hashed request coverage independently of transport cursors.
Routine renewal opens a second authorized read feed after 20 seconds, keeping
the current feed until a valid replacement catches up. The server's 25-second
lease remains unchanged. The Model owns both subscription slots and retires old
runs; at most two read-only feeds overlap per tab.

## Local operator onboarding

Configure Google locally with the exact redirect URI
`http://localhost:4331/api/auth/callback/google` (or the chosen canonical origin).
Use the Google account named in the invitation. Sign-in requests account selection;
a wrong-account invitation page offers sign-out and retains the invitation path.
Only team, diagram and invitation paths under `/app` and `/join` are accepted continuations.
Actual provider credentials, consent and callback acceptance remain an operator
qualification; the tests use synthetic identities and do not complete Google OAuth.

Set `ZLOZ_OPERATOR_TOKEN` in the app's ignored `.env` to a value generated by
`openssl rand -hex 32`, then start/restart the local stack. The future first owner
must sign in once: bootstrap requires an existing verified identity linked to
Google. It never creates or verifies an identity.

From the repository root, preview the exact change:

```sh
bun run --filter @opsydyn/zloz-team bootstrap --owner-email owner@example.com --name 'Pilot team' --slug pilot-team
```

Review the returned name/slug, then repeat with `--apply`. A matching repeat returns
`existing`; an existing slug with a different name/owner fails. The CLI accepts
only a loopback HTTP backend origin (default `http://127.0.0.1:1337`, override with
`--backend-url`). The optional `ZLOZ_BACKEND_PORT` changes that backend port. It
reads its token from the environment, never command arguments. The default task targets loopback only. M4 adds an explicit `--staging` option
for the approved staging origin and its disabled-by-default bearer-protected bridge. Organization and first-owner insertion share one
D1 batch so a failed membership insertion rolls the organization back.

The owner opens their team from `/app`, creates an invitation for a named email,
and selects/copies its read-only link to share themselves. No email is sent.
Invitations last seven days. Owners can cancel links, change roles and remove
members. There must always be an owner, and the pilot cap is ten members. Invite
links cannot be reused after acceptance and subsequent membership removal.
An expired invitation can be cancelled before creating a replacement.

The directory is tenant-scoped metadata. Owners/editors can create a blank diagram
or import an exported graph; viewers can open and export. The existing public
local workbench remains separate.
Directory recency is a best-effort projection that can lag edits by up to one
second; canonical versions and durable edit acknowledgements remain authoritative.

The runtime suite includes Chromium desktop/mobile and keyboard form checks.
Install its pinned browser if absent with
`cd apps/zloz-team && bunx --no-install playwright install chromium`.
Screenshots of synthetic test users are written to `zloz-m1-*.png` in the system temporary directory.
See [ADR 0037](../../docs/adr/0037-deliver-invited-team-onboarding.md) for the
onboarding contract and boundaries.

## Milestone 2 operation qualification

The private [`foldkit-zloz-alchemy`](../../packages/foldkit-zloz-alchemy) workspace
now hosts the shared core operation contract in a Domain aggregate. The guarded
test topology adds an operation fixture Worker with real Durable Objects, signed
sessions and current D1 membership checks. It is not imported by the normal
application topology and adds no public graph writer. The test suite checks
serialized edits, duplicate and changed-payload races, scope isolation and safe
Undo. The dev/test scripts build their workspace integration dependencies first,
so a fresh install does not depend on another app having generated `dist`.

## Shared editing (M3)

Open a team and choose **Create or import a diagram**. Imports accept an exported
ZLOZ graph JSON file or pasted JSON and always create a new diagram. Supported
shared edits are add, drag/keyboard move, width resize, rename, connect, delete,
atomic group/port deletion and **Undo my last edit**. Layout, grouping/reparenting,
full replacement, rich-text merging and snapshot Redo are outside this slice.

One edit may be in flight per browser. Gestures and label drafts are marked as
unsaved; completed actions save automatically. An uncertain save retains its exact
request and ID for **Retry saved request**. A receipt cannot replace newer graph
state. The browser warns before leaving unsaved work, but unsent browser state is
not crash-persisted. Export reads the server's canonical graph. Presence expires
within 15 seconds of its last heartbeat and also disappears on process restart.

Pilot caps: 250 nodes, 500 edges, 1 MiB of authored graph data and a 1 MiB request
body. Team membership remains capped at ten. Five concurrent editors is a target,
not measured capacity. The local suite covers two isolated Chromium sessions,
request/feed ordering, lost replies, authorization and native process restart.
Provider login, hosted restore/load/cost and release acceptance are M4 gates.

## Release qualification and owner recovery (M4)

Owners can download a target-bound checkpoint and preview/apply it as a new
canonical version from **Backup and recovery**. Stale previews conflict; exact
retries keep their identity. Recovery advances field clocks, clears old Undo and
retains event history and consumed IDs. Editors/viewers cannot invoke recovery.

The private adapter now emits ESM/declaration artifacts for isolated tarball
consumers. The runbook documents native packed-consumer and five-editor workload
commands, staging resources, Google setup, bootstrap, migration, recovery, rollback
and cost qualification. These commands do not establish hosted acceptance by
themselves. See [ADR 0040](../../docs/adr/0040-qualify-zloz-team-release-and-recovery.md).

## C4 workspace appearance

The team app uses vanilla-extract through its Astro/Vite configuration.
`src/styles/workspace.css.ts` owns app-wide semantic palettes and maps them into
the existing `--flow-*` canvas tokens. The engineering shell uses restrained
gradients, a structural grid, clipped panels, mono controls and a stable selection
inspector. Responsive layouts stack the rails rather than hiding actions.

**System**, **Light** and **Dark** are personal browser preferences. A validated
`zloz-team-theme` cookie supplies the server-rendered preference; the header
The Effect UI model controls live styling, and a command persists the cookie. This
non-sensitive cookie contains only the theme name. System follows OS changes.
Failed persistence keeps the chosen palette usable for the current visit.
The live stylesheet requires modern CSS `:has` and `color-mix` support.

**Canvas emphasis** offers **C4 view**, **DDD view** and **Neutral view**. C4 uses
green/cyan; DDD uses amber. This local appearance choice does not convert, filter,
relabel or save graph content. Existing architecture metadata determines each
node's type label and default icon. Untyped nodes retain a generic cube.

Selected Phosphor Core assets are compiled into static definitions with the private
`@opsydyn/foldkit-phosphor` adapter. To regenerate them, first build that workspace,
then run `bun tools/generate-icons.ts` from this app directory. The compiler also
copies the upstream licence to `public/third-party/PHOSPHOR-LICENSE`. No SVG parser
or full icon catalogue is included in the client rendering path.

See [ADR 0042](../../docs/adr/0042-style-zloz-teams-as-a-c4-workspace.md).
Under **Selection inspector → Node icon**, editors can choose a built-in icon
or upload a PNG or WebP to the shared team library. Images are limited to 64 KiB
and 512 × 512. The team can reuse an icon across diagrams. Owners can archive
icons, and existing boards keep displaying them. SVG exports embed available
team icons. The export review reports when an image is unavailable or exceeds
the SVG image budget. See [ADR 0125](../../docs/adr/0125-share-node-icons-through-the-team-library.md).

## Aggregate view

Choose **Aggregate** in **Inspector view** and select an aggregate or aggregate root on the canvas. Viewers, editors and owners can inspect its handled commands, emitted events and activated policies. The panel follows confirmed team edits, including renames and removals. Inferred links are labeled. Browsing uses the existing canvas selection and requires only diagram read access.

## Balanced Coupling inputs

In the selection inspector, choose **Assess relationship**. Owners and editors
can author abstraction scope, expected-change horizon and all four inputs:
integration type (intrusive, functional, model or contract), strength, distance
and volatility. Each judgment needs a basis and rationale; unknown inputs need
an explicit reason. Save shares the evidence live with the team. Viewers can
read the form and refresh the shared snapshot but cannot author changes.

Drafts remain local and survive incoming live updates. A competing revision
blocks saving until **Load shared assessment (discard draft)** is used to review
it. Graph changes make saved evidence stale; explicitly review the relationship
against the current diagram before saving again. Network uncertainty preserves
the exact original request for **Retry assessment request**, avoiding duplicate
or changed-payload writes. Graph Undo, export and recovery checkpoints do not
include assessments. Closing/discarding or reloading the page loses unsaved drafts.

This is qualitative evidence authoring. It adds no coupling chart or numeric
risk score. POST `/api/zloz/diagrams/:team/:diagram/assessments` is the sole public
assessment writer; the existing authenticated frame/live feed exposes saved
records. Deploy a compatible backend before this frontend; see ADR 0044 for the
new durable event and rollback constraint.

## Bring an Alchemy stack onto a board

For Teams staging, generate a snapshot from the trusted stack with the approved
local staging profile and environment. Run from the repository root first to
build the adapter, then generate the snapshot from the app directory.

```sh
bun run --filter @opsydyn/foldkit-zloz-alchemy build
cd apps/zloz-team
bun --env-file=/absolute/path/to/staging.env tools/staging-infrastructure-snapshot.ts \
  "$(git rev-parse HEAD)" /tmp/teams-staging.infrastructure.json
```

The command reads the pinned Alchemy plan and creates a new JSON file. In Teams,
open **New diagram**, choose **Alchemy infrastructure**, and load the file.
Review the canvas and its unresolved references. Select a finding to focus the
resource. Acknowledge the losses and choose **Create team diagram**. Teammates
can select an imported resource to inspect its stack, stage, and source
revision. Plan action labels describe the capture and do not invoke Alchemy.

On an empty shared board, editors can instead choose **Import…** beside
**Add node** and review a LikeC4 view or Alchemy snapshot in place.
**Import into this board** applies the reviewed graph as one shared edit with
one Undo. A newer confirmed version invalidates the preview even if a
teammate's Undo makes the board empty again.
